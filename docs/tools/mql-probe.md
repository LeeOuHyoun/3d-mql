# MQL 응답 지연 측정 (mql-probe)

확장에서만 두 번째 요청부터 MQL 응답이 느려지는 원인을 가리기 위한 측정입니다. mql 이 설치된 현장 PC 에서 한 번 실행합니다. 확장을 거치지 않고 확장과 같은 방식(`mql -k` 를 파이프로 띄움)으로 mql 에 조회 명령만 보내 응답 시간을 잽니다.

## 배경 (지금까지 조사한 내용)

현상: 접속 직후 첫 MQL 실행이나 검색은 잘 되는데, 두 번째 요청부터 어떤 요청이든 응답이 크게 느려집니다. 무거운 조회 때문이 아니며, 같은 MQL 을 cmd 창의 mql 에서 직접 실행하면 바로 나옵니다.

가짜 mql 에 실제 확장 코드(호스트와 웹뷰)를 물려 조사한 결과입니다. 실제 mql 로는 확인하지 못했습니다.

배제된 원인
- 확장이 두 번째 요청 앞에 끼워 넣는 MQL: 콘솔에서 연달아 실행할 때는 0개였습니다.
- 확장의 출력 처리 속도: 정상적인 mql 이라면 두 번째 요청도 수 ms 에 처리됩니다. 10만 줄 출력이나 웹뷰 화면 처리도 병목이 아니었습니다.
- 응답 끝 표식(`print context;` 출력)이 사라지는 경우: 60초 뒤 오류나 엉뚱한 결과가 나옵니다. "느리지만 맞는 결과"와 맞지 않습니다.

남은 유력한 원인 (실제 mql 에서 미확인)
- 파이프로 띄운 mql 이 쉬는 동안 입력을 점점 드물게 확인하는 경우: 바로 이어 보낸 요청은 빠르고, 결과를 보고 다음 명령을 치는 사이 쉬고 나면 느려지며, 결과는 맞게 옵니다. cmd 는 키보드 입력을 바로 받으니 즉시 나옵니다. 말씀하신 증상 세 가지가 모두 맞습니다.
- 그래프 조작 직후에는 확장이 한 번에 여러 명령을 보내는데 mql 이 실행 중 도착한 입력을 버리는 경우: 이 경우는 60초 뒤 오류나 엉뚱한 결과가 나옵니다.

그래서 확장을 거치지 않고 mql 의 응답 시간만 먼저 재어 원인을 확정합니다. 확정 전에는 확장 코드를 고치지 않습니다.

## 준비

1. VS Code 설정의 `3d-mql.contextCommand` 값을 복사합니다. 확장이 접속할 때 쓰는 `set context user ... password ... ;` 문장입니다.
2. 오래 걸리지 않는 조회 명령 하나를 정합니다. 예: `temp query bus Part * * limit 10 select id;`

## 스크립트 받기

3d-mql 폴더는 소스코드 저장소 폴더이며, VS Code 설치 경로나 설치된 확장 폴더가 아닙니다. 설치된 확장에는 이 스크립트가 들어 있지 않으므로 파일 하나만 받으면 됩니다.

1. 브라우저에서 `https://github.com/LeeOuHyoun/3d-mql/blob/main/docs/tools/mql-probe.ps1` 을 엽니다. 저장소가 비공개이면 GitHub 에 로그인합니다.
2. 오른쪽 위의 다운로드 아이콘(Download raw file)으로 바탕화면 등 아무 곳에 저장합니다.

저장소를 이미 받아 둔 PC 라면 `git pull` 뒤 `docs/tools` 폴더의 파일을 쓰면 됩니다.

## 실행

PowerShell 에서 스크립트를 저장한 폴더로 이동해 실행합니다. 바탕화면에 저장했다면 다음과 같습니다. `<...>` 두 곳만 바꿉니다.

```
cd $HOME\Desktop
powershell -NoProfile -ExecutionPolicy Bypass -File .\mql-probe.ps1 -Login "<contextCommand 값>" -Query "<조회 명령>"
```

- 약 2분 30초 걸립니다. 화면에 `waiting 10s (idle)` 같은 줄이 나오는 것은 일부러 쉬는 구간이니 멈춘 것이 아닙니다.
- 실행하는 동안 VS Code 의 3d-mql 탭은 쓰지 마세요. 측정에 섞입니다.
- 비밀번호는 결과 파일에서 `****` 로 가려집니다. 다만 화면의 명령 입력 줄에는 보일 수 있으니, 결과를 전달할 때는 요약 부분만 복사합니다.
- 조회 명령만 보내며 데이터를 바꾸는 명령은 보내지 않습니다.

## 결과

끝나면 화면에 요약이 나오고, 같은 폴더에 `mql-probe-result.txt` 도 생깁니다. 요약 전체를 전달해 주세요.

| 항목 | 내용 |
| --- | --- |
| A1 ~ A3 | `print context;` 를 쉬지 않고 연속 3회 |
| B0 | 조회 명령, 쉬지 않고 |
| B3 · B10 · B30 | 3초 · 10초 · 30초 쉰 뒤 조회 명령 |
| C10 · C30 | 10초 · 30초 쉰 뒤 `print context;` |
| D | 30초 동안 1초마다 `print context;` 를 보낸 뒤의 지연과 조회 시간 |
| E | 오류가 나는 명령과 `print context;` 를 한 번에 보냈을 때 뒤 명령이 살아 있는지 |
| F | 조회 명령 실행 중에 뒤따라 보낸 입력이 버려지는지 |

## 보는 법

- B10 · B30 · C10 · C30 이 수 초로 크게 나오면: 쉬었다 보낸 요청이 느린 것입니다. 파이프로 연결된 mql 이 쉬는 동안 입력을 점점 드물게 확인하는 경우입니다. D 가 빠르면 확장이 쉬는 동안 가벼운 명령을 주기적으로 보내 mql 을 깨워 두도록 고칩니다.
- E 나 F 에 `DROPPED` 가 나오면: mql 이 입력을 버리는 것입니다. 명령을 한 번에 하나씩만 보내고, 어긋나면 다시 맞추도록 고칩니다.
- 모든 값이 수십 ~ 수백 ms 로 고르면: mql 은 정상이고 확장 안쪽 문제입니다. 단계별 시간을 나눠 기록하는 로그를 넣어 출력 창(Output)의 `3D MQL` 로그로 원인을 짚습니다.
